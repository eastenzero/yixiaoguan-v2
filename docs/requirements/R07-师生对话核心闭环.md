## 三、R07-2 · AI 暂停 / 恢复策略补齐

### 目标状态

> 真实教师一旦接入会话，AI 立即停止继续抢答；人工处理完成后，学生下次提问时 AI 可以重新接管，形成清晰、可预期的多角色协作策略。同时补齐 R07-1 遗留的"学生侧状态守卫"。

### 核心策略（T0 默认方案）

除非 TX 明确要求"resolve 即刻回到 ai_serving"，本任务默认沿用并固化以下策略：

1. `accept`：`pending_teacher → teacher_serving`
2. `teacher_serving` 期间：学生消息只写库 + WS 广播，**绝不调 Dify**
3. `resolve`：`teacher_serving → resolved`
4. 学生后续再发消息：`resolved → reactivate → ai_serving`，然后恢复 AI 回复

**好处**：

- `resolved` 保留为可审计状态
- AI 恢复时机明确，由学生下次提问触发，避免教师刚点 resolve 就被 AI 插话
- 兼容当前代码骨架，改动面最小

### 改动范围

| 组件 | 改动 | 执行者 |
|------|------|-------|
| `services/gateway/app/routers/chat.py` | 明确只在 `ai_serving` 调 Dify；`teacher_serving` / `pending_teacher` 下只写库 | T3 Executor |
| `services/gateway/app/routers/conversations.py` | 学生分支补状态守卫（R07-1 遗留）：`closed` 拒绝 403；`resolved` 触发 reactivate | T3 Executor |
| `services/gateway/app/services/state_machine.py` | **不改 TRANSITIONS 表**，仅可能补充文档注释 | T3 Executor |
| `services/gateway/tests/test_ai_pause_resume.py` | 新增单测覆盖 accept/resolve/reactivate + Dify mock 断言 | T3 Executor |

### 验收标准

| 层级 | 判定 | 实际结果 |
|------|------|---------|
| L0 | 教师 accept 后 Dify 不再被触发；教师 resolve 后学生下次发消息 AI 正常恢复 | ✅ PASS |
| L1 | `pytest` 通过；覆盖 accept/resolve/reactivate 主链路、`teacher_serving` 下禁止 Dify、非法状态等；ruff / mypy 通过 | ✅ 9 passed / ruff OK |
| L2 | 手工验证完整链路：`student escalate → teacher accept → student 发消息只收 JSON 不收 SSE，gateway 日志无 Dify 请求 → teacher resolve → student 再发消息重新得到 AI SSE 回复` | ✅ PASS（e2e 脚本阶段 C/E/F） |
| L3 | WS 时间线可观察到 `pending_teacher → teacher_serving → resolved → ai_serving` 完整状态流，AI 在人工介入期间 0 次回复、恢复后仅回复 1 次 | ✅ PASS（e2e 脚本阶段 F.4/G.3/G.4 锁住 `status_changed(ai_serving, previous_status=resolved)` 事件顺序） |

### 已知陷阱

- 若把 `resolve` 直接改成 `ai_serving`，会丢掉"教师已解决"的显式审计状态；**除非 TX 明确确认，不做此改动**
- `chat.py` 里 `resolved` 分支和普通状态校验的先后顺序不能乱，否则会出现学生在 `resolved` 下被 403 的问题
- 仅靠前端隐藏 AI 输入框而后端仍允许调 Dify，会出现"看似暂停、实际抢答"的假闭环
- `teacher_serving` 期间学生消息仍需写库和广播，否则教师看不到学生的补充信息

### 回滚方案

- Git revert 本次改动即可
- 若状态机被改坏，优先恢复到当前的 `accept → teacher_serving → resolve → resolved → reactivate → ai_serving` 既有链路

## 四、R07-3 · `escalate` 时广播学院教师工单通知

### 目标状态

> 学生呼叫人工后，不只是把会话状态改成 `pending_teacher`，还要把"有新工单待接"这件事主动推给对应学院的在线教师，避免教师必须靠轮询列表页发现新单。

### 核心策略（T0 默认立场）

1. **只同学院 teacher 收到通知**。admin 不参与 escalate 广播对象，避免权限边界模糊
2. **离线教师忽略**。由 `ws_manager.send_to_user` 是否有连接决定；不做补投递
3. **通知失败不阻塞 escalate**。状态转换成功即视为主流程完成；教师 WS 发送失败仅记 log
4. **payload 字段最小但稳定**：`conv_id` / `student_id` / `title` / `status` / `created_at`

### 改动范围

| 组件 | 改动 | 执行者 |
|------|------|-------|
| `services/gateway/app/routers/actions.py` | 锁定 `_notify_college_teachers()` 的 `college_id` 筛选语义，补异常容错 | T3 Executor |
| `services/gateway/app/services/ws_manager.py` | 按需补 `broadcast_to_college_teachers` 的参数校验（不重构连接层） | T3 Executor |
| `services/gateway/tests/test_escalate_notify.py` | 新增单测覆盖同学院收到、跨学院收不到、无在线教师不报错等 | T3 Executor |

### 验收标准

| 层级 | 判定 | 实际结果 |
|------|------|---------|
| L0 | 学生执行 escalate 时，状态转 `pending_teacher`，并广播 `escalation_notify` 给同学院在线教师 | ✅ PASS |
| L1 | `pytest` 通过；覆盖同学院收到、跨学院收不到、学院无在线教师不报错等场景；ruff / mypy 通过 | ✅ 5 passed / ruff OK |
| L2 | 手工建立至少 3 个教师连接（同学院 2 + 其他学院 1），触发 escalate 后只有同学院在线教师收到完整 payload | ✅ PASS（e2e 脚本阶段 B.3/B.4/B.5——教师收到 + 5 字段 payload）；**B.7 锁住 admin 不收到** |

### 已知陷阱

### 定位为回归资产

- **连接三个角色 WS** 并并行断言，这是单测无法多角度覆盖的部分（特别是 “admin 不在广播列表里”）
- **锁住 WS 事件顺序**：如 G.4 验证 `status_changed` 事件 index < `new_message` 事件 index，防止当前还正确的 reactivate 顺序被后续重构意外打破
- **锁住 content-type**：区分 `application/json` vs `text/event-stream` 能捕捉“看似返回但走错分支”
- **过程行招**：使用 `drain_messages` 而非后台协程来规避 websockets 库的 `ConcurrencyError: cannot call recv while another coroutine is already running recv`
