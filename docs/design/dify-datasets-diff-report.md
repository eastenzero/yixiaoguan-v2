### 6.2 建议走哪条路

**建议：B. 切草稿 Dataset**

具体动作：
1. **Gateway 端**：修改 `services/gateway/.env` 的 `DIFY_GLOBAL_DATASET_ID`，从 `ec072e85-ebb3-4f2a-a966-a21566b88995` 切换为 `4db0c819-7847-4a95-bf06-5b73a9d41d70`，然后重启 gateway。
2. **Dify UI 端**：在 Dify 控制台将当前 Chatflow **草稿发布**（点"发布"按钮），使生产流量使用草稿版配置——草稿版的知识检索节点已经指向 `4db0c819-...`（Draft Dataset）。
3. **无需重新跑 `migrate_kb.py`**：Draft Dataset 中的 835 条数据已经就是 v2 数据，重新导入会造成重复和 API 浪费。

### 6.3 为什么不选 A 或 C

| 选项 | 判定 | 理由 |
|------|------|------|
| **A. 已完成** | ❌ | Published Dataset 只有 432 条，不是 835 条；gateway 也未指向 v2。不能标 ✅。 |
| **C. 重新灌** | ❌ | Draft Dataset 已包含 835 条 v2 数据，内容格式、数量、时间线全部吻合。重新创建 Dataset 是无效劳动，且存在 API 限流和重复数据风险。 |

### 6.4 附风险点

1. **Gateway 与 Chatflow 不同步风险**：如果只改 gateway `.env` 但不发布 Chatflow，gateway 调用的 Dify Chatflow 生产版仍会使用 Published 的 Dataset ID（因为 Chatflow 的 Dataset 绑定是在 workflow 节点配置里，不是 gateway 传参决定的）。**必须两步都做**（gateway 切 ID + Dify UI 发布草稿）。
2. **Draft 中 111 条带 `[KB-V2-...]` 后缀的 title**：如果 Dify 的检索或展示逻辑对 `[]` 敏感，需观察是否影响召回。建议切换后抽测 3-5 个典型问题验证 RAG 命中。
3. **Published 中 317 条 v1 独有数据将下线**：切换后这些旧条目不再可用。若其中包含仍有价值的内容（如某些节假日通知），需确认是否已吸收进 Draft 的 835 条中。从重叠率仅 115 条看，大部分旧数据确实已被替换。
4. **本地 final-merged/ 未直接访问**：本报告基于 PG 直查 + 旁证推理，未做本地文件逐 title diff。如 TX 希望 100% 确认，可在 Windows 本地运行 task 文件 Step 3 的 `comm` 命令做最终校验。
5. **PG `kb_entries` 表仍为 432 条**：`yx_postgres` 的 `kb_entries` 表尚未同步 v2 数据（仍为旧 v1 的 432 条）。如需同步，需另行执行迁移脚本或手动更新。此问题超出本 Scout 任务范围，建议由 r06-2 Executor 处理。
